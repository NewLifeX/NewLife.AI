# 工具参数类型化 vs JSON 字符串 —— 性能与体积基准报告

> 测试日期：2026-08-20 ｜ 环境：net10.0 / Release / InProcessEmitToolchain / BenchmarkDotNet 0.15.8
> 目的：用数据验证「工具参数类型化根治」的真实代价，回答"强类型会不会明显变慢/变大"

## 1. 测试目标

对比 `IList<TimelineItem>`（类型化）与 `String items`（JSON 字符串）两种工具参数方案的：

| 维度 | Benchmark | 说明 |
|------|-----------|------|
| 参数解析性能 | `ToolArgParsingBenchmark` | 完整工具调用链路（ToolRegistry.ConvertValue → 类型转换）|
| 内存分配 | `ToolArgParsingBenchmark` | 每次解析的托管内存 |
| 参数 Schema 体积 | `SchemaSizeBenchmark` | 发给模型的工具声明字节数（≈token 开销）|

## 2. 参数解析性能（5 条 vs 50 条）

演示 POCO：`BenchItem { Date, Title, Description, Color, Category }`（5 字段，与真实 `TimelineItem` 一致）。

| 方法 | 均值 | 分配 | 相对基线 | 分配比 |
|------|------|------|---------|--------|
| String_5（基线） | 3.224 us | 6.91 KB | 1.00 | 1.00 |
| String_50 | 26.005 us | 53.75 KB | 8.07 | 7.78 |
| **Typed_5** | **7.808 us** | **18.20 KB** | **2.42** | **2.63** |
| **Typed_50** | **75.285 us** | **170.89 KB** | **23.35** | **24.7** |

### 关键读数（诚实呈现）

- **类型化比字符串解析慢 ~2.4x（5 条）/ ~2.9x（50 条）**，内存多 ~2.6x / ~3.2x
- 原因：类型化路径走 `JsonHelper.Convert`（IList→POCO 反射转换），字符串路径仅 `JsonNode.Parse` 后按索引取值
- **但绝对值为微秒级**：50 条也仅 75 us、171 KB

## 3. 参数 Schema 体积

| 方法 | 均值（构建耗时）| 分配 | Schema 字节数 |
|------|----------------|------|---------------|
| String 版本 | 3.429 us | 3.46 KB | **196 字节** |
| Typed 版本 | 6.086 us | 7.09 KB | **399 字节** |
| 比例 | 1.77x | 2.05x | **2.04x** |

### 关键读数

- 类型化 schema 体积 **196 → 399 字节（+203 字节）**，约 2 倍
- 换算 token：英文/JSON 结构约 3~4 字节/token，增量 **≈ 50~70 token**
- 这是发给模型的**单次固定开销**，每轮对话都要携带，但相对完整请求（工具声明 + 历史上下文，通常上万 token）**增量 < 0.5%**

## 4. 分析

### 4.1 性能代价可以忽略

| 对比对象 | 类型化解析耗时 | 占比 |
|----------|---------------|------|
| LLM 工具调用一次（网络往返 + 模型生成） | 数百 ms ~ 数秒 | **< 0.01%** |
| 类型化解析 50 条参数 | **75 us** | — |

75 微秒相对秒级工具调用完全不可感知，且解析只在收到工具参数时发生一次，不在热点循环内。

### 4.2 Schema 体积代价换来什么

| 方案 | 模型看到的声明 | 可靠性 |
|------|---------------|--------|
| String（196 字节） | `"items": {"type": "string", "description": "JSON 字符串..."}` | 依赖模型**手工转义** JSON-in-JSON，元素间多余引号即解析失败（本次事故根因）|
| Typed（399 字节） | 完整 `array → object` 字段结构（Date/Title/Description/Color/Category）| 模型直接生成结构化 JSON，`ConvertValue` 自动转换，无转义环节 |

+203 字节（≈50~70 token）换来：**零转义错误、无需 LLM 重试、可靠渲染**。一次失败的重新生成成本远高于此。

### 4.3 与主流产品一致

OpenAI / Anthropic / Gemini 的工具调用全部采用 **JSON Schema 强类型**（`parameters: {...}` 声明完整对象结构），不提供"让模型传 JSON 字符串"的路径。类型化是行业标准做法。

## 5. 结论

| 项 | 类型化代价 | 是否值得 |
|----|-----------|---------|
| 解析性能 | 微秒级（50 条 75 us），相对 LLM 调用可忽略 | ✅ 值得 |
| 内存 | 170 KB @50 条，单次一次性 | ✅ 值得 |
| Schema 体积 | +203 字节（≈50~70 token）| ✅ 值得 |
| 可靠性收益 | 消除转义错误、无需重试、模型看到完整结构 | — |

**类型化的代价（微秒级解析 + 少量 schema 体积）远小于收益（消除转义错误、无需重试、可靠渲染），且与 OpenAI/Anthropic/Gemini 主流做法一致。** 数据支持本次"类型化根治"决策正确。
