# NewLife.AI 协议客户端分析

> 版本：v2.0 | 日期：2026-08-03
> 范围：`NAI/NewLife.AI/Clients/` 协议客户端部分的 **chat / stream / think** 基础对话与增强对话能力。工具（Tool）相关由独立分析覆盖，不在此文档展开。

---

## 1. 概述

本文档对 `NewLife.AI` 基础库的协议客户端部分做深入分析，目标是**确保所有支持的协议类型和模型服务商在 chat / stream / think 上稳定可靠使用**。

分析覆盖：
- 6 类协议实现（OpenAI Chat Completions、Anthropic Messages、Google Gemini、DashScope 原生、Ollama 原生、AWS Bedrock Converse）
- 37+ 个 OpenAI 兼容服务商（`BuiltinChatClient` 注册）
- 专用客户端（DeepSeek、AzureAI、NewLifeAI 多协议网关）

## 2. 协议客户端总览

### 2.1 架构

主体系为 **`AiClientBase` / `IChatClient` + `AiClientRegistry`**：

```text
AiClientRegistry（[AiClient] / [AiClientModel] 特性扫描注册）
  └─ AiClientDescriptor（无状态描述符 + Factory）
       └─ IChatClient 实例（AiClientBase 子类，绑定 Endpoint/ApiKey）
            ├─ GetResponseAsync          → 非流式
            └─ GetStreamingResponseAsync → 流式
                 └─ ChatStreamAsync（协议级 SSE/NDJSON 解析）
```

统一契约：
- `IChatRequest` / `IChatResponse`：跨协议统一请求/响应接口
- `ChatRequest` / `ChatResponse`：内部统一传输模型
- 各协议请求 DTO（`ChatCompletionRequest`/`AnthropicRequest`/`GeminiRequest`/`DashScopeRequest`/`OllamaChatRequest`/`BedrockRequest`）实现 `IChatRequest` 并实现 `FromChatRequest`/`ToChatRequest` 双向转换
- 各协议响应 DTO 实现 `IChatResponse`，统一暴露 `Messages`/`Usage`/`Text`

### 2.2 协议客户端清单

| 协议 | 客户端 | 基类 | 认证 | 端点形态 |
|------|--------|------|------|----------|
| OpenAI Chat Completions | `OpenAIClientBase` / `OpenAIChatClient` | `AiClientBase` | Bearer | `{endpoint}/v1/chat/completions` |
| OpenAI 兼容服务商（37+） | `BuiltinChatClient`（`partial OpenAIChatClient`） | `OpenAIChatClient` | Bearer | 各自 `ChatPath` 覆盖 |

### 2.3 遗留体系清理（Phase 0）

原 `Providers/` 目录下 7 个旧 Provider 类（`IAiProvider`/`OpenAiProvider`/`AnthropicProvider`/`DashScopeProvider`/`GeminiProvider`/`NewLifeAiProvider`/`OllamaProvider`）为旧协议实现，已通过 `<Compile Remove>` 排除编译，运行时已全部改用 `AiClientRegistry`（`ModelService`/`GatewayService`/`模型配置.Biz`/`ModelPricingService` 均走 `GetDescriptor`）。经全工作区引用检查确认无任何代码依赖后，已于 2026-08-03 删除，并同步清理 `NewLife.AI.csproj` 的 `<Compile Remove>` 条目与 `IChatClient.AsBuilder` 的过时示例注释。

## 4. chat — 基础对话能力

### 4.1 统一请求构建

各协议通过 `FromChatRequest(IChatRequest)` 将统一请求转换为协议 DTO：
- `ChatCompletionRequest.FromChatRequest` / `BuildBody`：字典方式构建，仅含非空字段（避免 qwen-max 等严格校验拒绝 null），支持多模态 `Contents`（text/image/audio）与工具消息
- `AnthropicRequest.FromChatRequest`：`system` 消息提升为顶级字段、`stop`→`stop_sequences`、工具 `tool_use`/`tool_result` 内容块
- `GeminiRequest.FromChatRequest`：`contents` 数组、角色 `model`（非 assistant）、`systemInstruction` 顶级字段
- `DashScopeRequest.FromChatRequest`：`input.messages` 嵌套、`parameters` 嵌套、多模态内容块
- `OllamaChatRequest.FromChatRequest`：`messages` + `options`
- `BedrockRequest.FromChatRequest`：Converse `messages` + `inferenceConfig`

### 4.2 统一响应解析

各协议响应 DTO 实现 `IChatResponse`：
- `ChatCompletionResponse`：`choices[].message` / `delta`，`usage`（`prompt_tokens`/`completion_tokens`）
- `AnthropicResponse`：`content[]`（text/thinking/tool_use），`usage`
- `GeminiResponse`：`candidates[].content.parts[]`，`usageMetadata`
- `DashScopeResponse`：`output.choices[]`，`usage`
- `OllamaChatResponse`：`message` + `done`
- `BedrockResponse`：`output.message.content[]`，`usage`

### 4.3 健壮性

- ✅ 非法 assistant 消息跳过：`ShouldSkipAssistantMessage`（DeepSeek 等要求 assistant 至少含 content 或 tool_calls）
- ✅ 版本路径去重：`CombineApiUrl` 防止 `{endpoint}/v1` + `/v1/...` 产生双版本路径
- ✅ 错误响应：`PostAsync` 非 2xx 抛 `ApiException`（状态码 + 响应体）
- ✅ 空消息校验：`AiClientBase.GetResponseAsync`/`GetStreamingResponseAsync` 空消息抛 `ArgumentException`

## 5. stream — 流式对话能力

### 5.1 各协议流式格式

| 协议 | 流式格式 | SSE 前缀 | 终止标记 |
|------|----------|----------|----------|
| OpenAI 兼容 | SSE | `data: `（带空格） | `data: [DONE]` |
| Anthropic | SSE | `event:` + `data:`（无空格） | `message_stop` |
| Gemini | SSE | `data: `（带空格） | 流结束 |
| DashScope 原生 | SSE | `id:`/`event:`/`data:` | 流结束 |
| DashScope 兼容 | SSE | `data:`（无空格） | `[DONE]` |
| Ollama | NDJSON | 无前缀，逐行 JSON | `"done":true` |
| Bedrock | SSE | `event:` + `data:` | `messageStop` |

### 5.2 已修复缺口（Phase 3，2026-08-03）

| # | 缺口 | 影响 | 修复 | 状态 |
|---|------|------|------|:---:|
| S1 | **Anthropic 流式用量丢失**：`AiClientBase.GetStreamingResponseAsync` 只取最后一个非空 chunk 的 Usage；Anthropic 的 input/output token 分 `message_start`/`message_delta` 两个互补 chunk 返回，流式路径 `InputTokens` 恒为 0。下游 `MessageFlow`（Web）与 `GatewayService`（网关）同样取末 chunk，导致**用量记录/会话 Token 统计/计费错误**。`MergeChunkUsage` 覆写仅在 `ToolChatClient` 路径生效 | 计费与统计错误 | `GetStreamingResponseAsync` 改用 `MergeChunkUsage` 合并并回写 chunk.Usage | ✅ |
| S2 | **SSE 前缀不统一**：OpenAI 兼容要求 `data: `（带空格），DashScope 兼容用 `data:`；`[DONE]` 在 DashScope 兼容路径被静默跳过继续循环 | 部分服务商返回 `data:`（无空格）时整行被丢弃，流式中断 | 统一前缀兼容判断（忽略大小写）+ `[DONE]` 统一 break | ✅ |
| S3 | **流式错误静默吞掉**：OpenAI 兼容 / DashScope 兼容 / NewLifeAI 路径 `try { ParseChunk } catch { }` 静默吞异常；流式 `error` 对象被当作普通 chunk 丢弃 | 协议变更/服务商错误无感知，表现为静默截断 | 新增 `AiClientBase.EnsureNoStreamError` 识别流式 `error` 对象并抛异常；Anthropic/Bedrock 处理 `event:error`；Ollama 处理 NDJSON error | ✅ |

### 5.3 已健壮的部分

- ✅ 取消令牌：各协议流式循环均检查 `cancellationToken.ThrowIfCancellationRequested()`
- ✅ Anthropic 流式事件模型完整：`message_start`/`content_block_start`/`content_block_delta`（text/thinking）/`content_block_stop`/`message_delta`/`message_stop`
- ✅ Ollama 流式 tool_calls 语义：`done=false` 中间帧出现 tool_calls 时，终结帧覆写 `FinishReason=ToolCalls`，保证工具循环正确进入
- ✅ DashScope 原生流式错误：`event:error` 时解析 code/message 并抛 `HttpRequestException`

## 6. think — 思考模式能力

- `ChatOptions.EnableThinking`（`Boolean?`）：null=不设置、true=开启、false=关闭

- 协议专属：`Items["ThinkingBudget"]`（DashScope 原生 `thinking_budget`）
