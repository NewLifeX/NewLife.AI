> **第 14 轮（2026-08-10）补充**：公共 API 表面审计 + 测试覆盖补强 + 性能基准与优化。
> - **A-109（性能）**：`HashTextEmbedder.Embed` 长文本分配热点（基准实测 200 句/7489 字分配 896.6 KB、Gen2 124.5 次高频回收）。根因：① Tokenize 物化 ~12600 个 token 字符串（~500 KB）；② tf 字典字符串键（~200 KB）；③ `Murmur128.ComputeHash` 每次调用分配 ~144 B（微基准实测，复用实例亦如此），且 `TryComputeHash` 抛 `The algorithm's implementation is incorrect`（NewLife.Core 缺陷，A-110）。优化为**混合去重哈希**：CJK unigram/bigram 用 Int64 打包键（`char` / `(char<<16)|char`）去重替代字符串键、英文单词保留 String 键（`ToLowerInvariant` 多字符展开语义）、复用单个 Murmur128 实例 + 8 字节 UTF8 缓冲、仅对唯一 token 哈希（调用数 ~12600→~2000）。效果：Embed_Long **459.5→152.8 µs（↓67%）**、**896.6→62.9 KB（↓93%）**、Gen2 124.5→0.24（消除）；Embed_Short 3.225→2.926 µs、8.13→6.3 KB。补 2 项黄金值测试（精确非零桶断言，锁定语义逐位一致）。**后续（内联零分配，见 A-110）再降**：Embed_Long **152.8→138.9 µs**、**62.9→22.85 KB（↓64%）**；Embed_Short **2.926→1.90 µs**、**6.3→3.77 KB（↓40%）**，逐 token 哈希分配归零。
> - **A-110（已修复）**：`Murmur128.TryComputeHash` 抛 `InvalidOperationException: The algorithm's implementation is incorrect`。根因：`Murmur128` 仅重写 `HashSize` 属性、从未设置基类受保护字段 `HashSizeValue`（默认 0），基类 `TryHashFinal` 校验 `final.Length(16) == HashSizeValue/8(0)` 失败即抛错（.NET 8/10 源码实证）。**已在 NewLife.Core 修复**：构造器设置 `HashSizeValue = 128`（权威修复，全 TFM 生效）+ `#if NET5_0_OR_GREATER` 补零分配 Span 路径（`HashCore(ReadOnlySpan)`/`TryHashFinal(Span)`），新增 7 项测试（TryComputeHash 与 ComputeHash 一致性、黄金值锁定双路径）。但 NAI 目标框架 net45/netstandard2.0/netstandard2.1 **无法编译 .NET 5+ 的 `TryComputeHash`**（netstandard2.1 引用程序集无该 API，实证确认），故 NAI 侧改用**内联零分配 Murmur128**（`ComputeMurmur128`，seed=0 逐位复刻写入预分配缓冲区，黄金值测试锁定输出逐位一致），彻底消除逐 token 哈希分配（见 A-109 效果）。
