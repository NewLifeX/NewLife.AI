## 测试目标

为 `NAI/NewLife.AI` 关键路径建立性能基线，识别热点并优化。基准项目位于 `NAI/Benchmark`（net10.0，Release 模式，MemoryDiagnoser）。

## 热点优化：HashTextEmbedder.Embed

### 定位

首轮全量基准显示 `Embed_Long` 分配 **896.59 KB / 459.5 µs**，Gen0/1/2 各 124.5 次——重度 GC 压力。短文本 `Embed_Short` 也分配 8.13 KB（22 字）。

### 根因分析

1. **字符串物化**：`Tokenize` 对每个 CJK 单字/双字创建字符串（`seg[i].ToString()` / `seg.Substring(i, 2)`），200 句文本产生 ~12600 个 token 字符串（约 500 KB）。
2. **tf 字典**：`Dictionary<String, Int32>` 以字符串为键去重（~2000 个唯一 token，约 200 KB）。
3. **Murmur128 每次调用分配 ~144 B**：`HashAlgorithm.ComputeHash` 的内部开销（含 16 字节结果数组）。微基准实测：复用实例每次仍分配 144 B，每 token 新建实例则 208 B。
4. **TryComputeHash 不可用**：`NewLife.Core` 的 `Murmur128.TryComputeHash` 抛 `InvalidOperationException: The algorithm's implementation is incorrect`（核心库缺陷，见 §5）。

### 优化方案（已实施）

**混合去重哈希**（`NAI/NewLife.AI/Embedding/HashTextEmbedder.cs`）：

1. **CJK token 用 Int64 打包键去重**：单字 `key = char`，双字 `key = (char<<16) | char`，替代字符串键——消除 ~500 KB 字符串物化，同时保留去重（去重使哈希调用数从 ~12600 降到 ~2000）。
2. **英文单词保留 String 键**：需 `string.ToLowerInvariant()` 语义（可能多字符展开，如 `İ → i̇`），逐字符转小写会改变语义。
3. **复用单个 Murmur128 实例**：`ComputeHash` 每次自动 `Initialize()` 重置状态，输出与每 token 新建实例逐位一致。
4. **复用 UTF8 编码缓冲**：CJK 单字/双字编码进 8 字节 `byte[]`，消除 `Encoding.UTF8.GetBytes(string)` 分配。

**数学等价性**：按唯一 token 累加 `count/total`，与逐出现累加 `1/total` 在 L2 归一化前逐位一致（归一化尺度不变性）。由新增**黄金值测试**（`HashTextEmbedderTests` 2 项）锁定，防止语义回归。

### 验证

- 新增 2 项黄金值测试（精确非零桶断言），全量测试 **1607 通过 / 0 失败 / 33 跳过**（基线 1564 → +43）。
- 输出向量与优化前逐位一致（黄金值逐桶断言通过）。

## 其余路径结论

- **VectorData / MessageParse / SchemaBuild / BuildBody / ToolLoop 全部健康**（µs 级、KB 级分配、无 Gen2），无需优化。
- `ToolChatClient` 工具循环：无工具调用 0.103 µs / 768 B；**完整一轮工具调用（模型请求→执行工具→第二轮收尾）仅 1.622 µs / 6.02 KB**——相对真实 LLM 调用（毫秒级）开销可忽略，工具循环不构成瓶颈。
- **流式 SSE chunk 解析**（v1.1 新增，Web 默认流式最高频路径）：文本 chunk 4.479 µs / 10.55 KB，工具 chunk 8.692 µs / 17.95 KB（含 tool_calls 图构建），结束 chunk 4.387 µs / 9.91 KB。
  - 时间成本相对 LLM 延迟（秒级）可忽略；每 chunk 10-18 KB 分配为 `ToJsonEntity<ChatCompletionResponse>` 反射式 JSON 反序列化的架构下限（第 8 轮审计已确认"流式解析无冗余分配"）。
  - 100 chunk 流式响应 ≈ 1-1.8 MB 短生命周期分配（Gen0 为主，廉价回收）；不建议冒险迁移自研解析器，收益（时间上无感、分配降级有限）不抵风险。

## 覆盖结论

已基准覆盖 14 个关键路径方法（嵌入/向量编解码/消息解析/Schema 构建/请求体构建/工具循环×2/流式解析×3），**唯一可优化热点（HashTextEmbedder）已修复**，其余均健康或处于架构下限。

## 遗留事项

| 事项 | 说明 | 建议 |
|------|------|------|
| `NewLife.AI.csproj` 的 `AssemblyVersion=1.5.*` 通配符 | 与 Deterministic 构建不兼容（CS8357），BenchmarkDotNet 等确定性消费者无法构建 | 评估改为 `<AssemblyVersion>$(VersionPrefix).0</AssemblyVersion>`（FileVersion 仍携带完整版本）；需确认 NewLife 版本体系约定 |
| `NewLife.Core.Murmur128.TryComputeHash` 抛异常 | 实测抛 `The algorithm's implementation is incorrect` | 属 NewLife.Core 缺陷，建议在 NewLife.Core 修复（若实现 TryComputeHash 可进一步消除 16 字节结果数组分配） |
